## The challenge and the solution

The trusted challenge imports Statement alone, which imports Mathlib. Five placeholder proofs declare the types to be met. The solution imports Statement and Paper.Approximate, never Challenge. Both sides name their declarations in the Solution namespace. A check that imports both or merely finds the name could inadvertently use a placeholder. We read back each type in its own environment. Axiom queries on the proof side give a second check on this failure mode. The Linux job separately compares the declarations and replays the exported proof in a second kernel. ## What each computation measures

1. **Original source.** Reconstruct the Git tree recursively from file bytes. Bind the 333 project blobs, toolchain, nine external package revisions, exact checker script and configuration before running proof code. The project has four default targets. The transitive union has 323 distinct Lean source modules. The publisher's five-declaration axiom-reporting script adds a 324th source. [Lock](../source-lock.json) · [Targets](../primary/vp-vnp/lakefile.toml)
2. **Native Lean.** Build every original project module in dependency order into an empty project-object directory, against the pinned external library objects. Reject proof-placeholder warnings outside Challenge. Compare full pretty-printed types under isolated Challenge and Solution imports, then query disjoint public and internal declarations on the solution side. The standard axiom allowlist is propositional extensionality, quotient soundness and classical choice. The reader script binds the per-module results to the original source bytes and verifies the coverage and queries offline. This computation checks the original proof terms. [Runner](../checks/pass14_release.py) · [Queries](../checks/pass14_release.lean) · [Local receipt](../checks/pass14_release.json)

It checked the pinned source and exact publisher checker blob, installed the checksummed elan bootstrap, and ran Lake and the publisher's driver against a disposable project copy. The script pins Comparator, nanoda and landrun, resolves a compatible lean4export tag, forces nanoda on, tests the allowed axioms, and requires both zero exit and the exact acceptance marker. The [original hosted ZIP](../checks/pass14_linux_artifact.zip) preserves the build log, exact configuration and full Comparator output. ## Reproduce

From the extracted packet or checkout, run `python3 checks/pass14_reader_check.py` for offline receipt/source integrity and finite controls. With Lean 4.33.1 and the built package revisions in the publisher manifest available, use `python3 checks/pass14_release.py --lean /path/to/lean --mathlib /path/to/mathlib --jobs 4 --work-dir /tmp/vpvnp14-objects --output /tmp/pass14_release.json`. Choose a previously absent work directory. Recheck the stronger result with `python3 checks/pass14a_margin_replay.py --lean /path/to/lean --mathlib /path/to/mathlib --objects /tmp/vpvnp14-objects/objects --output /tmp/pass14a_circuit_results.json`. On a disposable Linux copy, change into `primary/vp-vnp`, install the pinned toolchain, run `lake exe cache get`, `lake build`, `lake env lean scripts/PrintAxioms.lean`, then `bash ../.github/scripts/comparator-check.sh`. The hosted workflow records the prerequisites and immutable setup choices. Do not use the project's immutable source copy as a build directory if you wish to keep it pristine.

The common mathematical input is the pinned Statement definition, the Lean theory with the permitted standard axioms, and its interpretation as the advertised problem. Success on all five endpoints covers the complete **encoded** separation. The review's independent contribution is the verification execution and the human and machine audits catalogued here. The approximate endpoints received formal coverage. Detailed human inspection in this edition concentrates on the exact proof. Independent rediscovery or an assessment of field-wide consensus would require different evidence.
